# oncofiles

AI-powered medical document management for cancer patients and caregivers. Connects Google Drive, Gmail, and Calendar to Claude, ChatGPT, and any MCP client.

## Quick start

```bash
uv sync --extra dev
uv run pytest
uv run ruff check
```

## Project structure

- `src/oncofiles/` — main package
- `tests/` — pytest tests
- `migrations/` — SQL schema migrations
- `data/` — local dev SQLite database (gitignored)

## Conventions

- Python 3.12+, async-first
- FastMCP 3.0+ for MCP server
- Pydantic for data models
- ruff for linting/formatting
- Filenames follow standard convention: `YYYYMMDD_PatientName_Institution_Category_DescriptionEN.ext`
  - Separators: underscores only
  - Description: English, CamelCase, max 60 chars
  - Category tokens: Labs, Report, Pathology, CT, USG, Genetics, Surgery, SurgicalReport, Prescription, Referral, Discharge, DischargeSummary, ChemoSheet, Reference, Advocate, Other, Vaccination, Dental, Preventive
  - Legacy formats (space+dash, underscore-separated) still parsed for backward compat

## Key commands

- `uv run oncofiles-mcp` — run MCP server (stdio)
- `MCP_BEARER_TOKEN=test MCP_TRANSPORT=streamable-http uv run oncofiles-mcp` — run HTTP server locally
- `uv run pytest` — run tests
- `uv run ruff check --fix` — lint and auto-fix
- `uv run ruff format` — format code

## Deployment

- **Self-hosted Mac mini** (since 2026-11-06): Coolify in a Colima Linux VM, Traefik + Let's Encrypt in front, `oncofiles.com` streamable-http at `/mcp`. Build pack Railpack, install `uv sync`, start `uv run oncofiles-mcp`. Forpsi and Railway are retired. Host/network details live in the private RUNBOOK, never in this public repo (no IPs, IDs, tokens).
- **Push to `main` deploys** via the CI `deploy` job (`.github/workflows/ci.yml`): after lint+test pass, the runner joins the tailnet as an ephemeral `tag:ci` node and POSTs to the Coolify API, then smoke-tests `/health`. Kill switch: repo variable `DEPLOY_ENABLED`. Always run `/deploy-check` after a push.
- **Env-only changes are cheap**: with an unchanged commit SHA, Coolify logs `No build configuration changed & image found … Build step skipped` and just recreates the container.
- **Never tick "Available at Buildtime"** on a new env var unless the build genuinely needs it — Railpack writes buildtime vars into a `.env` that `mise`/`aqua` read (#550).
- **DB is a local SQLite file** (aiosqlite, WAL) on the Coolify volume, path `DATABASE_PATH`. There is no cloud DB option: any non-empty `TURSO_*` env var makes startup fail (`server._assert_local_database`, #617). Data survives rebuilds; a failed deploy keeps the old container running.
- **Google**: a dedicated GCP project, named in the RUNBOOK (OAuth client, External / In production / unverified, 100-user cap accepted). `GOOGLE_INTEGRATION_ENABLED` stays `false` until the curated-folder pipeline (#562) ships.
- CI is lint + test + deploy.

## Infrastructure gotchas

- **Curated Drive folders are write-protected from legacy code (#562).** A patient root holding both `README.md` and `_index.json` is curated by its own contract (fixed folder set, sidecars, never delete). `curated_folder.mark_if_curated()` runs wherever a patient `GDriveClient` is built (`_create_patient_clients`, lifespan, `/api/gdrive-set-folder`) and sets `write_block_reason`; every write method on the client (`upload`, `update`, `create_folder`, `rename_file`, `move_file`, `trash_file`, `copy_file`, `create_shortcut`, `set_app_properties`, `grant_access`, `batch_*`) then raises `DriveWriteBlockedError`, which the retry decorator never retries. `sync`, `sync_to_gdrive`, `sync_from_gdrive` and `ensure_folder_structure` return early. Detection **fails closed** (listing error → curated). Only the contract pipeline may lift the block, via `with gdrive.contract_writes():`. Lock tests: `tests/test_curated_folder.py`. When adding a new Drive write method, call `self._guard_write("<name>")` first and add it to `WRITE_CALLS` in that test.
- **Curated-folder pipeline (#562, `src/oncofiles/curated/`)** is the only code allowed to write into a curated folder, and only inside `gdrive.contract_writes()`. Its Drive writes go through `curated/drive_ops.py`: read-back verification, **no retries**, no deletes (only its own canary is trashed). `DriveOps.move_rename` requires `allowed_parents` (the curated tree ids) and refuses `None`; an AST lock in `tests/test_curated_originals_invariant.py` checks every curated call passes it (#811). **Originals invariant:** an original source file (PDF, image, any non-text file) in a curated folder is never deleted, trashed or overwritten, only moved/renamed inside the curated tree with an undo record in the run journal; the helpers enforce it themselves (`drive_ops.update_text` only on `.md/.json/.jsonl/.txt/.tmp` with a text mime, `trash_canary` only on `_healthcheck.tmp`, `move_rename` keeps the extension and stays within `allowed_parents` = the walked tree), and so does the legacy client (`GDriveClient.update` only on `.md/.txt/.json/.jsonl` text/JSON non-Google-native files, `trash_file` only on an empty folder, both raise `DriveWriteRefusedError`); lock test `tests/test_curated_originals_invariant.py` (incl. an AST scan: no `.files().delete(` anywhere, Drive service writes in curated code only in `drive_ops.py`, trash bodies and media updates only in `drive_ops.py`/`gdrive_client.py`). Runs are **dry runs by default**. MCP: `curated_folder_run` runs in the background (local OCR takes minutes per page, which outlasts an MCP call); poll `curated_folder_status`. OCR and classification use the **local** LM Studio model via `LOCAL_LLM_BASE_URL` / `LOCAL_LLM_MODEL` / `LOCAL_LLM_API_KEY` (runtime-only env; from the container the host is `host.lima.internal`). Never route document content to a cloud model in this path. A misread date can never rename a file: `classify.validate` requires the date to be printed in the text and not to be a README birth date. Benchmark (#565): printed Slovak excellent, old handwriting weak; dedicated OCR research is #570, split/merge is #569.
- **Month-precision dates (#919, maintainer decision 2026-11-21).** A document whose printed date has only a month and a year is filed with the day-zero date token (`YYYYMM` followed by a zero day, with a real month; `naming.date_precision` is the ONE date rule of `build_filename` and `is_standard`/`parse_filename`: a real calendar day or that day-zero token, never a zero month or another partial form). `classify.validate` accepts a model `doc_date` of `YYYY-MM` only when that month and year is printed on its own (`classify.month_in_text`: numeric month/year, ISO year-month or a Slovak/Czech month name with the year; not inside a full date, not in a birth context) and it is not the README birth month, not in the future, not implausibly old (the same checks as a day); a printed day always wins. The sidecar gets `doc_date: "YYYY-MM"` + `doc_date_precision: "month"` (day sidecars are unchanged). `normalise` renames month-only filed notes (`2027-03-…`, sidecar `doc_date: "YYYY-MM"`) through the same journaled `move_rename`, then writes those two keys into the SIDECAR only (`set_date_precision`, journaled, key-only edit, body byte for byte). **An original is never written, text notes included (maintainer rule): a standard name with the day-zero token MEANS month precision**, so a note without a sidecar is only renamed; the indexer and `document_stage.document_month` read the sidecar key when present, else the filename token. Lock: every `update_text` in runner/normalise targets a sidecar, the canary, the README or a state/log file (AST + behavioural tests). The indexer stores such a row with `document_date` NULL (never a day printed nowhere: facts, timeline and lab dating read `document_date` as a day) and `doc_date_precision: "month"` + `doc_month: "YYYY-MM"` in `structured_metadata` (INDEX_VERSION bumped); `document_stage.document_month` makes it dated (never `missing_date`), `/api/documents` and `/api/doc-detail` return the date as `"YYYY-MM"`, the dashboard shows it as month/year. Tests: `tests/test_919_month_precision.py`.
- **Self-service curated bootstrap (#853, `curated/bootstrap.py`).** `/api/gdrive-set-folder` (the New Patient wizard) makes every non-curated folder curated before connecting it: the README contract comes from `curated/templates/README_<patient_type>.md` (display name, letters-only token, DOB, empty §3 vocabularies; the folder set IS the template's §2 table) and is validated with `parse_contract` before any write. Only into a folder that is not My Drive, not another patient's connected folder nor inside one (`db.list_other_patient_folder_ids`), not curated / inside / above a curated folder, has **no subfolders** and none of the state files (or a canary); a missing DOB refuses before anything (including a new folder) is created; the wizard then asks for it and resends `date_of_birth`, which `store_dob_if_missing` validates (real date, not future, not before 1900) and stores only when the context has none. A new folder's parent is checked first (`check_new_folder_parent`: not another patient's folder nor inside one, not curated nor inside one; My Drive is fine), so a refusal leaves no empty folder. Loose files in the folder are **not moved**: the pipeline treats root files as inbox candidates and files them on its first real run after the preview. Writes run inside `gdrive.contract_writes()` through `drive_ops` (read back, never retried, nothing deleted; `drive_ops.create_folder` exists only for this): `_actions.jsonl` first as the write-ahead journal (`planned` lines, then `done`), folders, `_changelog.md`, `_index.json`, **`README.md` last** — a half-done bootstrap is not curated, nothing processes it, a retry on that folder is refused. No canary, so the #734 deletion allowlist did not grow. Then the folder is persisted, `mark_if_curated` blocks legacy writes and the patient is enrolled (`set_curated_nightly(..., updated_by="self-service (#853)")`); continuous mode picks it up (settle time, preview first). Refusals: 409 `code: bootstrap_refused` + `reason`, bilingual `error`/`error_sk`; write failure 502 `bootstrap_failed`; nothing persisted in either case. The legacy category folders need `layout: "legacy"`, admin-only. The code lives in `drive_folder_link.connect_folder(..., bootstrap=True)` (the route passes `bootstrap=layout == "curated"`, `create_subfolders=layout == "legacy"`; the MCP tool never bootstraps). The #852 gate (`_dashboard_onboarding_refusal(request, "set_folder")`) runs before the body is read, so closed mode refuses a non-admin before any Drive call; the bootstrap write entry points are in `tests/test_onboarding_gate.py::SENSITIVE_REFS`. Templates keep `Standard version` + `## 3.` so #854's automatic vocabulary can extend them. Locks: `tests/test_853_curated_bootstrap.py` (only tools/curated.py and the bootstrap call `contract_writes()`; only the bootstrap writes `README.md`).
- **Dashboard upload (#921, `POST /api/upload?patient_id=…`, multipart `files`).** ACL before the body is read: `_dashboard_body_patient`, then `_dashboard_write_refusal` (only the patient's own caregiver; an admin's read-only view and the operator bearer get 403 `read_only`). `dashboard_upload.handle_upload` checks type by extension AND content (PDF, JPEG, PNG, HEIC/HEIF, TIFF, WebP, UTF-8 `.md`/`.txt`), refuses raw genotype exports (`.vcf`/`.csv`/`.tsv`, and notes that `llm_input.extraction_exclusion` excludes), enforces `MAX_FILE_BYTES` per file and `MAX_FILES` per request (one file per request: memory stays at one file, each file is read, stored, released and closed before the next), the document cap before any write; the rate limiter's own body limit for this path is `RATE_LIMIT_UPLOAD_MAX_BODY_BYTES` (one file plus multipart framing, refused before reading). **Curated patient:** `curated/inbox_upload.upload_to_inbox` resolves the inbox from the README §2 contract (`Contract.inbox`) and writes each file unchanged with `drive_ops.upload_original` (create-only into a live `00-inbox…` folder whose parent is the patient's curated root, never overwrites, never forms/adopts a sidecar pair, no state names, read back by size + md5, never retried) inside `contract_writes()` on a `dedicated_copy()`; a clash gets a numeric suffix before the extension; the first failed write stops the request; no patient lock and never a run or job (not in `run_active()`, so CI deploys never wait on an upload; a file landing mid-run is new work for the next probe). It is the third `contract_writes()` caller and the only `upload_original` caller (locks: `tests/test_853_curated_bootstrap.py`, `tests/test_921_dashboard_upload.py`). Inbox files show in the table only once filed (the read model does not index the inbox). **Non-curated:** the #777 Drive-only upload (`tools.documents.store_drive_only_upload`) whatever the cloud setting, suffix instead of superseding. A folder overlapping a curated tree or failing its check → `folder_not_writable`. Logs: counts, sizes, mimes, `name_len` only. Frontend: one request per file, sequential (XHR for progress); a reset, timeout or 502/504 (the proxy's read timeout per request) shows "too slow, try Wi-Fi or a smaller file", never an automatic retry; `/demo` sends nothing (XHR chokepoint next to the fetch one) and shows invented "Waiting for extraction" rows.
- **Curated runs vs deploys (#581).** A run executes in-process; a deploy or restart kills it. The canary `_healthcheck.tmp` is the run's write-ahead **journal** (line 1 `<run_id> journal-v1`, then one JSON line per action, written and verified *before* the action). `_actions.jsonl` is only appended at the end, so after a kill the canary is the only record. Next real run: canary older than 5 min with no journaled actions → trashed and the run continues; with actions, a legacy canary (no journal), or a fresh one → abort for a human. At startup `mark_interrupted_curated_runs()` flips stale `running` rows to `interrupted`, and the loop waits `STARTUP_GRACE_S` (5 min) so a rolling deploy's old container is gone. Never trigger a manual Coolify deploy while CI is deploying the same commit (2026-11-08: two deploys in 2 min killed a run). Each Drive client used by a run is a `dedicated_copy()` (httplib2 is not thread-safe, #577/#579). Each journaled action is followed by `{"ok": seq}` once verified (a pair only after both moves); a canary whose every action is confirmed is **recovered automatically** (actions carried into the next run's logs), any unconfirmed action still stops for a human. Shutdown calls `request_stop()`: a run finishes its current document and writes its logs. CI's deploy job waits (max 20 min) while `/health.curated_run_active` is true and then FAILS rather than kill a run (re-run the job once idle).
- **Google API clients: one service per thread (#579).** Rule: a googleapiclient service / `httplib2.Http` is never used by two threads at once and never crosses threads (httplib2 is not thread-safe; two threads on one TLS connection gave `SSLError: record layer failure` in #577 and are the suspected cause of the SIGSEGV series of mid-November 2026). Enforced in `google_service.py`: `GDriveClient`, `GmailClient` and `CalendarClient` are `PerThreadServiceMixin`s, so `client._service` is the CALLING thread's service, built lazily from the bundled discovery document (no network, cheap; the cost is one TLS connection per client and thread); `_rebuild_service()` and `close()` touch only the calling thread's connection; credentials stay shared with refresh behind a lock (`serialize_refresh`). Always read `client._service` in place where the request is executed (`client._service.files()…execute()`): never store it, pass it to `asyncio.to_thread` or return it, and never call `googleapiclient.discovery.build` or create an `Http` outside `google_service.py`. `dedicated_copy()` is still used by curated jobs (own connection, own `contract_writes()` scope, which stays thread-local) and is made inside the worker function. Lock tests: `tests/test_google_client_threads.py` (`test_entry_points_never_pass_a_service_across_threads` plus the AST locks).
- **Automatic README vocabulary (#854, `CURATED_AUTO_VOCAB`, default `true`).** A new Institution / Doctor is no longer a review reason.
  `classify.validate(auto_vocab=True)` proposes it for the README vocabulary section only when its spelling is printed in the sidecar text
  (folded exact match on word boundaries, outside a birth context; the prompt's `institution_printed` field, the doctor's surname).
  Never the patient's own name; `?` in the reading → `Unknown`; a README token after folding or a snap → that token.
  **Doctor tokens never carry a title (#900):** `naming.doctor_surname` is the ONE function for the filename doctor field (`surname_token`) and the vocabulary proposal; it drops academic/professional titles (MUDr, MDDr, MVDr, PharmDr, RNDr, PhDr, JUDr, PaedDr, Mgr, Bc, Ing, PhD/Ph.D., CSc, DrSc, MPH, MBA, prim, doc, prof, …; `naming.TITLES`) case/dot-insensitive, spaced or glued (`MUDr.Mgr.Jana`, `MUDrMgrJana`, `NovaPhD`; a glued title is recognised only in its mixed-case spelling, so an all-caps surname is never cut), before or after the name, then takes the surname (last word; `Surname, Given` form; a hyphenated surname stays one word). The token matches README §3 case-insensitively first (`snap`, `resolve_new`); `naming.has_title` is a last guard: a token that still holds a title is filed as `Unknown` and never added. Tests: `tests/test_900_override_and_titles.py`.
  A printed near neighbour of a different entity (the snap rule of #754) → review. Unknown institution/doctor alone → filed as `Unknown`.
  Review stays for another person, no/birth date, unknown type, split, low confidence.
  The runner writes the README **before** the document's sidecar (`readme_vocabulary_add`, journaled in the canary first, `update_text` read-back, no retry,
  aborts if the README changed since the run read it); one write per document that brings new tokens, later documents see them.
  `curated/vocabulary.py` edits only a managed block at the end of the vocabulary section (`<!-- oncofiles:auto-vocabulary v1 -->`,
  one changelog-style line per token incl. the printed form) and re-parses: anything but "old contract + new tokens", or an unknown layout
  (no `Standard version`, no vocabulary section, malformed/unknown block) → review (fail closed).
  Every dry run previews it whatever the env says: `report.vocabulary` has `auto_vocab_enabled`, `planned` (+ count), and per document `outcome_without` / `outcome_with`
  (`would_file_with_auto_vocab`), from a pure second validation against a shadow README; with the env off it also previews documents held only for vocabulary.
  The env gates every real effect (README write, filing on new tokens, re-queue). Server logs carry counts + `token_digest` only.
  Old sidecars held only for vocabulary are re-queued while it is on; `false` restores the old review behaviour.
- **Continuous mode (default, `CURATED_CONTINUOUS=true`).** The curated loop probes each enabled patient every `CURATED_POLL_S` (120 s) with `runner.probe()` — one tree listing, sidecars read only when the tree fingerprint changed since the last idle probe, no model calls. When new work exists and the youngest inbox file is older than `CURATED_SETTLE_S` (120 s), it runs a short sequence (`trigger="auto"`, `CURATED_CHUNK_DOCS`=5 docs per run, preview reused within 24 h). Overlap: one run per patient; files landing mid-run are pending on the next probe. A sequence that moves nothing parks its pending ids until something new arrives; a failed one backs off 30 min doubling to 4 h. The nightly sweep at `CURATED_NIGHTLY_HOUR` stays as the full catch-all. The per-patient flag `curated_settings.nightly_enabled` enrols a patient in all of it (startup index, continuous processing, nightly sweep), so the admin toggle is labelled "Automatické spracovanie" / "Automatic processing", never "nightly run" (#665); the column, `/api/admin/curated/nightly` and its `nightly_enabled` field keep their names. LLM load: a run makes one model call at a time, so it holds 1 of LM Studio's parallel slots.
  **Fair turns on the one shared model (#855, `tools/curated.continuous_round`).** A round probes every enabled patient, then gives each patient with settled work ONE bounded turn (preview if needed + one real run of `CURATED_CHUNK_DOCS`); ordinary patients first (rotating start), the active onboarding patient last; while turns move work the next round starts after `ROUND_PAUSE_S` (5 s), else after a poll. **Onboarding** = first import unfinished (no real run ever ended ok with `inbox_drained`; pre-#855 rows: empty `not_processed`) AND ≥ `CURATED_ONBOARDING_MIN_PENDING` (10) runnable items. At most one onboarding patient gets turns; others wait FIFO (already started first, then `curated_settings.updated_at`), blocked reason `onboarding_queue`; the slot is released when the import drains or the patient has nothing runnable. Queued onboarding patients are also skipped by the nightly sweep. **Before every OCR** the runner checks the document cap (`MAX_DOCUMENTS_PER_PATIENT` vs max(DB count, filed in tree) + documents OCR'd this run) and the per-patient UTC-day page budget `CURATED_DAILY_PAGE_BUDGET` (300, 0 = off; model pages of fresh vision extractions, previews included, persisted as `report.model_pages`); a held file stays in the inbox untouched, listed in `report.held` with its reason (`document_cap` / `daily_page_budget`), for every trigger. Over budget the loop and the nightly sweep skip the patient until the next UTC day (`daily_page_budget`). Visibility: `probe_stats()` (`onboarding`, `onboarding_queue_position`, `pages_today`, `page_budget`, `last_held`, `held_total`) and `heartbeat_detail().scheduling` — operator `/readiness` and the admin overview only, never `/health`.
- **The curated loop never waits on a patient lock** (starvation fix, 2026-11-11): a re-OCR/re-read job holds `patient_lock(pid)` for hours, and the old loop awaited it inside `_execute`, stalling probes for every patient. Now probes always run (read-only, from `PROBE_STARTUP_DELAY_S`=15 s after boot); only the RUN waits — for `STARTUP_GRACE_S`, failure backoff, or `run_block_reason(pid)` (this patient's own run, re-OCR/re-read job or held lock; never another patient's job, never an LLM shadow job). Background runs pass `skip_if_busy=True`; a blocked run is logged at INFO once per poll and retried. Per-patient counters (`probe_stats()`: `last_probe_at`, `probes_total`, `probes_skipped`, `runs_blocked`, `last_auto_run_at`, `pending_inbox_count`) are on operator `/readiness.curated_probes` and the admin curated overview, never on public `/health`.
- **Re-OCR loss guard (#660).** Before `curated/reocr.run_reocr` overwrites a sidecar it runs, next to the lab-vocabulary `lost_values` check, a generic `token_loss` over every printed number and date (front matter and page markers stripped, `12,5` = `12.5`, `5.3.2027` = `05.03.2027` = `2027-03-05`): any lost date (`REVIEW_MISSING_DATES` = 0), more than `REVIEW_MISSING_NUMBERS` = 2 lost numbers, or a near-empty page (< `NEAR_EMPTY_CHARS` = 50 chars) together with any lost number or a body below `NEAR_EMPTY_CHARS_RATIO` = 0.8 of the old one means `review` — the sidecar is not touched (no backup, no update; the new text is only kept as a candidate, see below); a blank page alone is not a stop. Reason codes in `review_reasons`, `decision` also on a dry run; report and log carry counts and page numbers only, never tokens.
  - **#806 (thresholds may only become stricter).** Also `review`: `text_shrunk` (new body < `TEXT_SHRUNK_RATIO` = 0.6 × old, with or without a near-empty page) and `low_word_overlap` (share of the old distinct words — NFC, lower-case, letters only, diacritics kept, ≥ `WORD_MIN_LEN` = 3 — found in the new text below `MIN_WORD_OVERLAP` = 0.40; reported as `word_overlap`). **Retry:** a vision pass (rewrite path only, never the verify-only re-read) answering < `NEAR_EMPTY_CHARS` while `reasoning_tokens / completion_tokens` > `RETRY_REASONING_RATIO` = 0.8 is asked ONCE more for that page with thinking off via the per-call marker (`llm.chat(thinking=False, reasoning_marker=True)`, same image/dpi/prompt; no LM Studio or env change); the retry's text is kept only when longer, a failed retry keeps the first answer, both calls are in `llm_passes` (the retry with `"retry": true, "thinking": "off"`), pages in `retried_pages`. **The reasoning channel is never a re-OCR transcript** (infra decision on #806; `reocr.py` must not even name `reasoning_content`, locked by a test). **Blank vs miss:** every rendered page gets `page_ink` (share of pixels darker than `INK_NEAR_WHITE` = 230 at `INK_DPI` = 36, rounded) and `page_text_layer` (PDF); a near-empty page with ink < `BLANK_INK_MAX` = 0.005 and no text layer is not retried; it is a blank back side (`blank_pages`, not counted by `near_empty_with_loss`) ONLY when the OLD sidecar has page markers and its text of that same page was < `NEAR_EMPTY_CHARS` too (`old_page_chars`). A Cowork-era sidecar without markers never has a blank page, and unknown ink is never blank: a blank must never loosen the guard (infra review of #809). A kept retry text goes through the same 2-pass `reconcile` and loss guard as any first pass. Lock test for the report fields: `tests/test_reocr_report_no_values.py`.
  - **`curated_restore_sidecar(document_id, backup_id, patient_slug, dry_run=True, reason)`** (admin-only, user-invoked, never scheduled): `backup_id` must be a file in the curated logs folder named `_reocr-backup-<date>[-<time>]-<that document's filename>.md` (else `refused: backup_not_in_logs` / `backup_not_of_this_document`); foreign document ids → `not_found`. Dry run: counts only (old/new chars, numbers, dates, missing/regained). Real run first makes the verified `pre_store.make_copy(db, "restore")` copy (kind `restore`, shared retention of 5; a failed copy refuses, writes nothing and releases the slot; the copy name is in the job `_restoring[pid]`, the report and the `activity_log` row), holds `patient_lock`, refuses while any run/job/index/restore is active (counts in `run_active()`, CI waits), and inside `contract_writes()` via `drive_ops`: copies the CURRENT sidecar to logs (`_restore-backup-<ts>-<filename>.md`), `update_text`s the sidecar with the backup (read-back verified), re-indexes the patient (`force_ids={document_id}`). One INFO line per attempt (`document_id`, `backup_id`, `verify=ok|failed|skipped`, result; no content). One `activity_log` row (ids, counts, `caller_email_hash`); `reason` is required (≤ 200 chars) and never stored or logged. Nothing is deleted. Core: `reocr.restore_sidecar`; tests `tests/test_reocr_retry_guard_restore.py`.
  - **A `review` keeps the new text as a candidate (maintainer decision 2026-11-15).** In a REAL run a `review` leaves the sidecar exactly as it is (old text stays primary; no backup, no re-index, no fact change) and writes the new transcription ONCE, inside `contract_writes()` via `drive_ops.create_text` (read-back verified, never retried), into the logs folder as `_reocr-candidate-<date>-<time>-<source filename>.md`: a header block (`kind: reocr_candidate`, `source_file`, `document_id`, `method`, `engine`, `dpi`, `passes`, `review_reasons`, `created`) followed by the complete sidecar text a rewrite would have written (`reocr.candidate_text`).
