# oncofiles

AI-powered medical document management for cancer patients and caregivers. Connects Google Drive, Gmail, and Calendar to Claude, ChatGPT, and any MCP client.

## Quick start

```bash
uv sync --extra dev
uv run pytest
uv run ruff check
```

## Project structure

- `src/oncofiles/` — main package
- `tests/` — pytest tests
- `migrations/` — SQL schema migrations
- `data/` — local dev SQLite database (gitignored)

## Conventions

- Python 3.12+, async-first
- FastMCP 3.0+ for MCP server
- Pydantic for data models
- ruff for linting/formatting
- Filenames follow standard convention: `YYYYMMDD_PatientName_Institution_Category_DescriptionEN.ext`
  - Separators: underscores only
  - Description: English, CamelCase, max 60 chars
  - Category tokens: Labs, Report, Pathology, CT, USG, Genetics, Surgery, SurgicalReport, Prescription, Referral, Discharge, DischargeSummary, ChemoSheet, Reference, Advocate, Other, Vaccination, Dental, Preventive
  - Legacy formats (space+dash, underscore-separated) still parsed for backward compat

## Key commands

- `uv run oncofiles-mcp` — run MCP server (stdio)
- `MCP_BEARER_TOKEN=test MCP_TRANSPORT=streamable-http uv run oncofiles-mcp` — run HTTP server locally
- `uv run pytest` — run tests
- `uv run ruff check --fix` — lint and auto-fix
- `uv run ruff format` — format code

## Deployment

- **Self-hosted Mac mini** (since 2026-11-06): Coolify in a Colima Linux VM, Traefik + Let's Encrypt in front, `oncofiles.com` streamable-http at `/mcp`. Build pack Railpack, install `uv sync`, start `uv run oncofiles-mcp`. Forpsi and Railway are retired. Host/network details live in the private RUNBOOK, never in this public repo (no IPs, IDs, tokens).
- **Push to `main` deploys** via the CI `deploy` job (`.github/workflows/ci.yml`): after lint+test pass, the runner joins the tailnet as an ephemeral `tag:ci` node and POSTs to the Coolify API, then smoke-tests `/health`. Kill switch: repo variable `DEPLOY_ENABLED`. Always run `/deploy-check` after a push.
- **Env-only changes are cheap**: with an unchanged commit SHA, Coolify logs `No build configuration changed & image found … Build step skipped` and just recreates the container.
- **Never tick "Available at Buildtime"** on a new env var unless the build genuinely needs it — Railpack writes buildtime vars into a `.env` that `mise`/`aqua` read (#550).
- **DB is a local libsql file** on the Coolify volume. Data survives rebuilds; a failed deploy keeps the old container running.
- **Google**: a dedicated GCP project, named in the RUNBOOK (OAuth client, External / In production / unverified, 100-user cap accepted). `GOOGLE_INTEGRATION_ENABLED` stays `false` until the curated-folder pipeline (#562) ships.
- CI is lint + test + deploy.

## Infrastructure gotchas

- **Curated Drive folders are write-protected from legacy code (#562).** A patient root holding both `README.md` and `_index.json` is curated by its own contract (fixed folder set, sidecars, never delete). `curated_folder.mark_if_curated()` runs wherever a patient `GDriveClient` is built (`_create_patient_clients`, lifespan, `/api/gdrive-set-folder`) and sets `write_block_reason`; every write method on the client (`upload`, `update`, `create_folder`, `rename_file`, `move_file`, `trash_file`, `copy_file`, `create_shortcut`, `set_app_properties`, `grant_access`, `batch_*`) then raises `DriveWriteBlockedError`, which the retry decorator never retries. `sync`, `sync_to_gdrive`, `sync_from_gdrive` and `ensure_folder_structure` return early. Detection **fails closed** (listing error → curated). Only the contract pipeline may lift the block, via `with gdrive.contract_writes():`. Lock tests: `tests/test_curated_folder.py`. When adding a new Drive write method, call `self._guard_write("<name>")` first and add it to `WRITE_CALLS` in that test.
- **Curated-folder pipeline (#562, `src/oncofiles/curated/`)** is the only code allowed to write into a curated folder, and only inside `gdrive.contract_writes()`. Its Drive writes go through `curated/drive_ops.py`: read-back verification, **no retries**, no deletes (only its own canary is trashed). Runs are **dry runs by default**. MCP: `curated_folder_run` runs in the background (local OCR takes minutes per page, which outlasts an MCP call); poll `curated_folder_status`. OCR and classification use the **local** LM Studio model via `LOCAL_LLM_BASE_URL` / `LOCAL_LLM_MODEL` / `LOCAL_LLM_API_KEY` (runtime-only env; from the container the host is `host.lima.internal`). Never route document content to a cloud model in this path. A misread date can never rename a file: `classify.validate` requires the date to be printed in the text and not to be a README birth date. Benchmark (#565): printed Slovak excellent, old handwriting weak; dedicated OCR research is #570, split/merge is #569.
- **Curated runs vs deploys (#581).** A run executes in-process; a deploy or restart kills it. The canary `_healthcheck.tmp` is the run's write-ahead **journal** (line 1 `<run_id> journal-v1`, then one JSON line per action, written and verified *before* the action). `_actions.jsonl` is only appended at the end, so after a kill the canary is the only record. Next real run: canary older than 5 min with no journaled actions → trashed and the run continues; with actions, a legacy canary (no journal), or a fresh one → abort for a human. At startup `mark_interrupted_curated_runs()` flips stale `running` rows to `interrupted`, and the loop waits `STARTUP_GRACE_S` (5 min) so a rolling deploy's old container is gone. Never trigger a manual Coolify deploy while CI is deploying the same commit (2026-11-08: two deploys in 2 min killed a run). Each Drive client used by a run is a `dedicated_copy()` (httplib2 is not thread-safe, #577/#579). Each journaled action is followed by `{"ok": seq}` once verified (a pair only after both moves); a canary whose every action is confirmed is **recovered automatically** (actions carried into the next run's logs), any unconfirmed action still stops for a human. Shutdown calls `request_stop()`: a run finishes its current document and writes its logs. CI's deploy job waits (max 20 min) while `/health.curated_run_active` is true and then FAILS rather than kill a run (re-run the job once idle).
- **Continuous mode (default, `CURATED_CONTINUOUS=true`).** The curated loop probes each enabled patient every `CURATED_POLL_S` (120 s) with `runner.probe()` — one tree listing, sidecars read only when the tree fingerprint changed since the last idle probe, no model calls. When new work exists and the youngest inbox file is older than `CURATED_SETTLE_S` (120 s), it runs a short sequence (`trigger="auto"`, `CURATED_CHUNK_DOCS`=5 docs per run, preview reused within 24 h). Overlap: one run per patient; files landing mid-run are pending on the next probe. A sequence that moves nothing parks its pending ids until something new arrives; a failed one backs off 30 min doubling to 4 h. The nightly sweep at `CURATED_NIGHTLY_HOUR` stays as the full catch-all. LLM load: a run makes one model call at a time, so it holds 1 of LM Studio's parallel slots.
- **Curated read model (#603).** `tools/curated.index_patient` mirrors a curated folder into `documents` so the chat tools (search, `view_document`, labs, timeline) see it: one row per filed source with `file_id = "gdrive:<drive id>"` (never uploaded to the Files API; `_try_download` goes straight to Drive), sidecar body → `document_pages` (`model = curated-sidecar`, so `view_document` never re-OCRs), front matter → date/institution/summary/`structured_metadata.curated`. Drive is only read; inbox/logs/duplicates are not indexed; a file that leaves the filed folders is soft-deleted. Runs after every successful real run, once at loop start, and via the `curated_index` MCP tool; incremental by sidecar `modified`. **Curated content never goes to a cloud model:** the "without AI/metadata" queries exclude `gdrive:%` rows, and every cloud-AI function in `enhance.py`/`doc_analysis.py` calls `curated.indexer.refuse_cloud(document_id, …)` right before `_get_client()` (registry loaded at startup from `db.curated_document_ids()`). When adding a new cloud-AI function, add the same guard. `search_documents` also matches page text.
- **Clinical facts model (#603, migration 072).** Facts live in `clinical_records` (extended): `code` → `fact_codes` (60 seeded codes, aliases, unit conversions), `param` = original label, `occurred_at` = sample time, provenance `source_document_id` + `page_number` + `evidence` (the exact text) + `extracted_by`, `verification` ∈ machine | unverified | verified | corrected. Entities: `organizations`/`departments` (shared), `practitioners` (**patient-scoped**), `encounters` (natural key per patient/day/org/dept/kind), generic `links` (both ends checked to be the same patient). Views `fact_series_v`, `latest_fact_v` (excludes unverified), `timeline_v`. Read tools in `tools/clinical_facts.py` (overview, timeline, fact_catalog, fact_series, document_detail, encounter_detail, people_and_places) are `readOnlyHint` and resolve the patient via `_resolve_patient_id`; statistics exclude unverified values unless asked. Re-extraction (`replace_document_facts`) soft-deletes machine facts with an audit row and never touches verified/corrected ones. Lab facts come from rule parsers (`curated/facts_rules.py`: Bory and NOÚ OKB formats), no model call; Cowork-era (non-local) sidecars yield `unverified` facts. A value printed under a date RANGE ("laboratórne 1.9.–9.9.:") is dated at the range **end** (`date_source=printed_range`, `date_precision=range`, both ends in `date_range_start`/`date_range_end`; #726 superseded the #659 midpoint, which produced a day printed nowhere). Anything comparing days across documents (fact_series dedupe, corroboration, `date_conflicts`, re-read keys, verified-fact protection) treats such a value as the whole window, never as one day. **Any change to what the parsers extract (rules, aliases in `fact_codes`, dating, corroboration) must bump `curated/indexer.INDEX_VERSION` in the same PR** — #668 shipped a parser fix without a bump, so production kept facts from two parser generations until the next full re-index surfaced 19 "unexplained" new rows (#672). Regressions compare against the production DB (infra exports per-doc code/date/verification plus a salted value hash; never raw values in a cloud-model session), not the old code against the new code.
- **Hard-data model, Phase 1 schema (#711, design `docs/architecture/hard_data_model.md`, migration 080).** Additive only, nothing moved: new tables `codings`, `provenance`, `devices`, `identifiers`, `conditions`, `cancer_stages`, `treatment_courses`, `treatment_cycles`, `medication_events`, `procedures`, `specimens`, `reports`, plus FHIR Observation columns on `clinical_records` (`result_status`, `value_comparator`, `unit_printed`/`unit_ucum`, `interpretation_code`, `effective_start`/`effective_end`/`effective_precision`, `issued_at`, `specimen_id`, `report_id`, `fhir_id`, `version_id`, `last_updated`; all NULL / 1 on existing rows) and nullable `fact_codes.plausible_low`/`plausible_high` (in `unit_canonical`, unseeded, for the generic verifier #714). Every fact table has `fhir_id` (UUID set by the writer), `version_id`, `last_updated`, `verification` (default `unverified`), soft delete and `patient_id NOT NULL`. Helpers live in `database/_hard_facts.py`: keyword-only `patient_id`, SQL-filtered, every patient-scoped reference (document, encounter, practitioner, condition, course, cycle, request, specimen) checked to be the same patient; `codings`/`identifiers.owner_type` and `provenance.target_type`/`activity`/`agent_role` are validated against Python allowlists (no CHECK, so they can grow without a table rebuild). Nothing reads these tables yet; no MCP tools until later phases. Do not backfill them in a startup migration. Tests: `tests/test_hard_facts_schema.py`.
  - **`identifiers` data minimisation:** never store a patient's national ID (rodné číslo) or insurance number (nor any MRN-like patient number) — for any owner. If matching on them is ever needed: only a salted hash, and only after a maintainer decision. `add_identifier` rejects such systems (and slash-form birth-number values) before anything else, then enforces a per-owner system allowlist (`IDENTIFIER_SYSTEMS_BY_OWNER`: ÚDZS provider code and IČO for organisations/departments, ÚDZS doctor code for practitioners, accession numbers for specimens/reports/documents). Extraction phases must not fill `identifiers` by default.
- **Local-only zones (policy 2026-11-09: background = local model only, cloud only when the user acts in Claude.ai).** `cloud_guard.local_only(job)` sets a ContextVar; `enhance._get_client()` and every Files API call (`FilesClient._guarded()`) raise `CloudForbiddenError` inside it, also in `asyncio.to_thread` workers. The curated index + fact extraction run inside it; the #619 backfill must too. New background jobs that touch documents go inside `local_only()`.
- **Session diary (`conversation_entries`, kept 2026-11-11, #721 follow-up).** `log_conversation` / `diary_add`, `search_conversations`, `get_conversation`, `get_conversation_stats`, `delete_conversation`, `restore_conversation` (`tools/conversations.py`) are a patient-scoped diary for Claude.ai / Claude Code / ChatGPT sessions, NOT deprecated with the other Oncoteam tools. Admins must pass `patient_slug`; foreign ids → `not_found`; participant from a fixed list; 20 kB/entry, 50 entries/patient/day; `document_ids` must belong to the patient; soft delete only. Diary text is local only: never to a cloud model, never to Drive (`export_manifest(include_diary=False)` in sync), never a fact source, and the audit middleware logs only `DIARY_AUDIT_SAFE_ARGS` for these tools. Any new module that reads the table fails `tests/test_session_diary.py::test_no_extractor_or_indexer_reads_the_diary`.
  Cloud AI is off by default (`CLOUD_AI_ENABLED=false`); the key alone doesn't enable it.
- **LLM-first extraction, shadow mode (#714 phase 2a).** `curated/llm_extract.py` asks the LOCAL model (one call per page of stored sidecar text, JSON schema + worked examples, `EXTRACTOR_VERSION`) for printed results with their verbatim evidence line; `curated/verifier.py` (generic, NO layout knowledge, `VERIFIER_VERSION`) decides `machine` vs `unverified` + reason codes (evidence on the page, label/unit/value digits inside the evidence, date printed and not a birth date, label → code via `fact_codes` aliases, unit conversion, plausibility). MCP `curated_llm_extract_preview(document_ids, patient_slug, dry_run=True)` is enabled by default (off-switch `LLM_EXTRACT_SHADOW_DISABLED=true`; no env needed, because it is dry-run only, explicit ids ≤ 10, local-only and refuses while another run is active), runs in the background inside `local_only()` holding one LM Studio slot (status via `curated_reocr_status`, kind `llm_shadow`), and reports per document only counts and codes (agreement on code + day + value hash, rule-only / LLM-only codes, unverified reasons, seconds). It writes NOTHING (no facts, no run row, no Drive) and does not block CI deploys. Never add per-layout parsing to the verifier; new labels are `fact_codes` aliases (data). Bump `EXTRACTOR_VERSION` on any prompt/schema change. Not stored, so no `INDEX_VERSION` bump. Plausibility ranges still live in `facts_rules.PLAUSIBLE`; they move into `fact_codes` in the Phase 1 migration.
  - Shadow report rules: a page whose answer is truncated (`finish_reason=length`), empty or unparseable is **not assessed** (`pages_not_assessed`) and is left out of the metrics on both sides, never counted as "LLM found none". The extractor uses the full `REASONING_BUDGET`, because LM Studio counts reasoning into `max_tokens` and may ignore thinking-off. Without a known DOB the report says `birth_date_guard: inactive_no_dob`; any future write path for LLM facts MUST call `verifier.require_dob_for_write()`.
- **Fixtures are synthetic only (maintainer rule, 2026-11-09):** test data, fixtures and docstring examples in this public repo use invented values AND invented dates (use year 2027 or later) — never lines copied from Drive, sidecars or any real document, even without names. A lab value plus its sampling timestamp is identifying health data. Real lines were copied into tests in #620/#634 and replaced in #637; history was kept (no rewrite). Enforced by `tests/test_synthetic_fixtures.py` (CI) and a local pre-commit hook on the maintainer's Mac that compares staged lines with the mounted Drive sidecars (outside the repo).
- **Public repo, real patients:** tests and fixtures for curated folders use **synthetic** names, institutions, doctors and Drive IDs only (`tests/fixtures/curated/`). Do not paste README examples, filenames or folder IDs from a real patient folder into code, tests, issues or PR text. Twice this session a test value was derived from a real ID or name and had to be replaced before commit. Real-data tooling (e.g. the OCR benchmark) lives in the private Drive next to the RUNBOOK.
- **A job's success signal must never be decoupled from whether it did any work (#552).** `_run_nightly_ai_pipeline` used to `continue` past every per-patient exception, so the job never raised, APScheduler fired `EVENT_JOB_EXECUTED`, and `job_tracker["nightly_ai_pipeline"]["last_ok"]` stayed fresh — a night where **every** patient failed was indistinguishable from a clean one. Combined with `_handle_sync_exception` only promoting `invalid_grant` to a health surface, `/health` returned `status: ok` for a month while all Google-backed processing was dead. Now the pipeline counts `sync_attempted`/`sync_failed` (incremented on **both** bail-out paths) and raises when they are equal and non-zero; `0 attempted` stays a success. When adding any batch job that swallows per-item errors, do the same, and prefer a **failure-mode-agnostic** staleness check over enumerating known errors — `db.get_last_successful_sync(patient_id=)` reads `MAX(finished_at) WHERE status='completed'`, whereas `get_sync_stats_summary.last_sync_at` is `MAX(started_at)` over all rows and stays fresh while every run fails.
- **`GOOGLE_INTEGRATION_ENABLED=false` is the Google kill switch** — use it, not `SYNC_ENABLED=false`, when Google credentials are dead. `SYNC_ENABLED` gates the entire APScheduler at `server.py:368`, taking `db_keepalive`, `memory_check`, the cleanup jobs and `sync_watchdog` down with it. The kill switch stops only Google-touching paths at two chokepoints: `_create_patient_clients` (returns `None` **before** any token load, so no refresh is attempted against a dead OAuth client) and the lifespan service-account fallback. Every caller already treats `None` as "not connected" and skips. `/health` reports `google_integration: "disabled"` so an intentional pause is never mistaken for health, and `sync_watchdog` suppresses its admin email while the switch is off.
- **`/health` must never touch the DB.** It is the liveness probe; blocking I/O gets the process killed at 120s. Staleness and other DB-derived telemetry are computed by the hourly `sync_watchdog` job and cached in `_sync_staleness` for `/health` to read. Locked by `test_health_makes_no_db_call`.
- **Don't classify `insufficientFilePermissions` as a credential failure.** `_hard_auth_reason()` matches project-deleted / API-disabled / dead-OAuth-client only. `insufficientFilePermissions` is #445's per-file ownership problem, which sync survives file-by-file; flagging it would permanently light up `/health` for patients whose Drive files are merely shared read-only.

- `/health` is a **liveness probe only** — NO DB calls, NO blocking I/O (Railway kills process at 120s)
- `/readiness` is the DB connectivity check (5s timeout) — use for dashboards, not healthchecks
- `reconnect_if_stale(timeout=10.0)` — always pass a timeout; unbounded reconnect cascades up to 105s
- Turso Hrana streams expire during idle — DB keepalive job pings every 4 min to prevent stale connections
- Coolify health check: `/health` on the app port, interval 30 s, timeout 5 s, 3 retries, start period 30 s (Railway's `railway.toml` was removed 2026-11-06)
- **Turso single-connection**: NEVER use `asyncio.gather` for concurrent DB queries — serialize them. Dashboard fetches must also be sequential (no `Promise.all`). The single libsql connection blocks under concurrent access.
- **uv.lock**: After bumping version in pyproject.toml, always run `uv lock` — Railway uses `--locked` flag which rejects stale lockfiles
- **Anthropic client singleton**: NEVER create `anthropic.Anthropic()` directly. Use `enhance._get_client()` — single shared httpx connection pool. Per-call client creation leaks SSL buffers (~1-5 MB each, never GC'd because SDK has no `__del__`). Caused P0 memory leak #366.
- **Dashboard i18n**: Uses `data-sk`/`data-en` attributes on elements. `applyDashLang()` queries all `[data-sk][data-en]` elements. Add both attributes when adding new user-visible text.
- **Multi-patient isolation**: ALL functions that use patient identity (get_patient_name, get_context, is_standard_format, rename_to_standard, parse_filename) MUST pass `patient_id`. The ContextVar fallback in `get_context()` catches missed callers during tool calls, but explicit is better. Never call `get_patient_name()` without patient_id in new code.
- **Cross-patient naming isolation**: Files must NEVER contain another patient's name in filename or folder name. After every `rename_documents_to_standard`, verify no cross-patient names leaked. The `_try_patient_name_swap()` in naming.py detects standard-format files with wrong patient name and swaps cleanly.
- **File operation safety**: Never lose original files during rename, split, or merge. GDrive rename is atomic (`files.update`). For split/merge: create new files first, only trash originals AFTER all parts confirmed. Trash only — never hard-delete (30-day soft delete per deletion policy).
- **Open signup + patient scoping**: `DASHBOARD_ADMIN_EMAILS` (config.py) controls who sees all patients. Non-admin session users only see patients where `caregiver_email` matches. `_get_patient_id(required=True)` raises ValueError when no patient selected — use `required=False` only for bootstrapping tools (list_patients, select_patient).
- **Document limit**: `MAX_DOCUMENTS_PER_PATIENT` (500 since #548, was 200) enforced at `insert_document()` DB level. Sync has its own FUP check (`fup_reached` flag). Both must remain in sync. **Never hardcode a numeric limit for a "every document for this patient" read** — use `config.DOC_QUERY_LIMIT`, which tracks the cap (and falls back to a 10k sentinel when the cap is `0` = unlimited, since `LIMIT 0` returns no rows). **25 call sites** hardcoded a numeric limit before #548, at `200`/`500`/`1000`/`10000`, spread across `sync.py`, `manifest.py`, `server.py`, `backfill_splits.py` and `tools/{hygiene,enhance_tools,export,naming,documents}.py`. Each silently dropped documents past its literal. The nastiest is `_cleanup_orphan_ocr`: it **trashes** any `*_OCR.txt` not in `expected_ocr_names`, so a truncated doc list soft-deletes legitimate sidecars. Next worst is `sync_to_gdrive`'s export loop — that `docs` list also feeds the rename and organize phases, so truncation silently excludes files from renaming/refoldering too.

  **`DOC_QUERY_LIMIT` is deliberately NOT equal to the cap** — it's `max(cap, 10_000)`. The cap bounds *future inserts*, not existing rows (q1b holds ~296 docs under a cap of 200), so a ceiling tracking the cap exactly would truncate reads over existing data whenever the cap is **lowered** — and then `_cleanup_orphan_ocr` trashes the sidecars of everything outside the window. `max()` keeps it monotonic; `10_000` also means adopting it never *lowers* a pre-existing literal. `LIMIT 0` returns no rows, so the `0 = unlimited` cap can't be reused as a limit either. Belt and braces: `list_documents` logs an **error** when `limit >= DOC_QUERY_LIMIT` and the result fills it, so truncation can never be silent again.

  Lock tests `tests/test_fup_document_limit.py` (16) sweep **all** of `src/oncofiles` for `list_documents(limit=<int>` and reload `config` under a patched env to prove a lowered cap doesn't lower the ceiling. Known-broken allowlist (hardcoded limit *and* missing the required `patient_id` kwarg from #499, so they `TypeError` before the limit matters): `migrate_to_turso.py`, `backfill_gdrive_ids.py`, `backfill_ocr.py`. That allowlist may only shrink. Still deliberately unconverted: `manifest.py`'s conversations/treatment/research reads (different tables, own volumes) and `landing.html`, which advertises 200 documents in 5 places incl. 2 JSON-LD blocks — public pricing copy, separate decision.
- **Patient types**: `patient_type` in patient context — `"oncology"` (default) or `"general"`. Controls folder creation (oncology skips vaccination/dental/preventive; general skips chemo_sheet/pathology/genetics), lab thresholds (mFOLFOX6 vs EU/WHO general health), and preventive care screening.
- **Stateless HTTP**: `stateless_http=True` in `mcp.run()` — no server-side sessions. Survives Railway deploys. Do not change to stateful unless SSE push is needed.
- **Patient isolation (bearer tokens)**: `verify_token()` in `PersistentOAuthProvider` sets `_verified_patient_id` ContextVar. Middleware reads this — NEVER access `_session._access_token` (doesn't exist in FastMCP 3.1.1 stateless mode). Auth paths: `onco_*` patient tokens → specific patient; static `MCP_BEARER_TOKEN` → default patient; OAuth → default patient; stdio → default patient.
- **HMAC key derivation (#502)**: NEVER use `MCP_BEARER_TOKEN.encode()` directly as an HMAC key. The bearer is reused for HTTP auth — leaking it would forge any HMAC tokens signed with it. Use `oncofiles.secrets_keys.dashboard_session_key(MCP_BEARER_TOKEN)` / `oauth_state_key(MCP_BEARER_TOKEN)` for purpose-bound derived keys. Adding a new HMAC purpose? Add a `_derive(...)` helper with a versioned purpose string (`oncofiles.<purpose>.v1`) and an optional dedicated env-var override (e.g. `DASHBOARD_SESSION_SECRET`). Tests must patch `oncofiles.config.MCP_BEARER_TOKEN` — `secrets_keys` reads it fresh at call time so module-local imports of the bearer don't bypass the patch.
- **Session token format (#510)**: `email|expiry|tid|sig` — single-owner parser is `_parse_session_token()` in `server.py`. Anything that needs to introspect the token (verify, extract tid, debug) MUST go through it; do NOT re-implement `rsplit(sep, 3)` elsewhere. The `tid` (16 hex chars) is the revocation handle: `POST /api/logout` writes it to `session_revocations` (migration 068) and adds it to the in-memory `oncofiles.session_revocation._REVOKED` denylist. Lifespan startup calls `load_from_db` + `purge_expired` so revocations survive Railway restarts. The set is currently unbounded between restarts (~50 bytes × 50k logouts ≈ 2.5 MB worst case, well under the 420 MB threshold) — if it ever matters, add a periodic `purge_expired` job behind `_sync_semaphore`. Legacy 3-part tokens still verify but cannot be revoked individually (they predate #510 and were already invalidated by the #502 key rotation).
- **Filename sanitization (#508)**: `oncofiles.files_api.sanitize_filename` is the single chokepoint for caller-supplied filenames. Apply at the upload boundary (`upload_document` does `safe_filename = sanitize_filename(filename)` BEFORE the value flows to `parse_filename`, the DB ownership/lookup query, the `Document(...)` constructor, or `gdrive.upload`). The sanitizer takes basename via `replace("\\", "/").rsplit("/", 1)[-1]` (so `../../etc/passwd` → `passwd`), regex-replaces forbidden chars, and strips leading dots. Backward-compat alias `_sanitize_filename` preserved for older imports.
